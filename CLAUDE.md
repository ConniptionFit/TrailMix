Prior: **2026-09-13 (v1.20.0)** — **a systematic audit of this file's own backlog turned up nine real, independently-fixed reliability/UX defects, on top of a full session's worth of AI/UX features and the sherpa-onnx migration finally reaching git.** The migration itself (AI-01/AI-12: Picovoice Falcon/Eagle replaced with sherpa-onnx, zero network permission restored) has its own writeup in the dedicated Falcon/Eagle Project-Facts rows below, and the AI-08 through AI-12/CAP-23/24/UX-22/23 feature batch is covered in the relevant Module Registry rows — this entry is the nine-item bug-fix pass that closed out the same session, all found by re-reading [[Future Improvements]]'s own To-Do table rather than from a new report. (1) **REL-16 — `pause()`/`cancel()`/`disableDeviceAudio()` blocked the main thread joining a pump thread.** `AudioPipeline.shutdown()`'s `micThread?.join(PUMP_JOIN_MS)` (up to 1s) ran inline on whatever thread called these — Compose click handlers and `CaptureService`'s notification action, both the main thread. New `launchAudioTeardown()` dispatches the actual `engine.endInput()`/`detachDeviceAudio()` onto the session scope instead; the one place that must not race ahead of it, `runListenSession()` (every path that can call `engine.begin()`), awaits the pending job first, so a fast pause-then-resume or cancel-then-start still serializes correctly without the caller ever blocking. Verified live: `ps -T` showed exactly one `trailmix-mic-pump` thread across a rapid pause→resume cycle, no duplicates. (2) **CAP-20 — three device-audio (playback) lane bugs.** `playbackPeak` was a `@Volatile Int` with a separate read-then-reset — visibility isn't atomicity, so a pump-thread bump landing mid-reset was silently clobbered a tick early; now an `AtomicInteger`. `detachPlayback()` nulled `playbackThread` without joining it, so a fast detach-then-reattach could run two pumps into one `ShortRingBuffer`; now joins first (the pump still owns releasing its own record in its own `finally` regardless of whether the join times out, per REL-12's rule). `ShortRingBuffer.push`'s false return (buffer full, chunk dropped) went unchecked; now logged, since a drop is real signal loss, not the same thing as the captured app legitimately being quiet. (5) **CAP-18** — `MlKitTranscriber.transcribe()` now closes the `pfd` it's handed in its own `finally`, guarded the same way `AudioPipeline`'s own close calls already are; previously only the ML Kit client was released on the graceful (non-abandon) teardown path. (6) **UX-21** — Home now scrolls to the top when the newest note's id changes, guarded to fire only when the user was already at/near the top (`firstVisibleItemIndex <= 1`); `LazyColumn` anchors scroll to the previously-first item by key, so a newly inserted note used to land just above the viewport and read exactly like a missing note — reproduced live during this same session's own verification pass before the fix. (7) **INT-05** — `DocumentFile.findFile` enumerates every child of the directory it's called on, and `tree.findFile(folderName)` (a full listing of the whole user-picked Export location tree) ran once per file written, independently, inside both `MarkdownExportWriter` and `PhotoExportWriter` — a note with a transcript and photos issued three full tree listings for one merge. `NoteExporter` now resolves and caches the folder once per export (re-validated with `exists()`, so a folder deleted outside the app is re-resolved rather than written into a dangling reference) and passes the resolved `DocumentFile` down to both writers. (8) **REL-18** — added indices on `notes.deletedAtEpochMs` (checked by every Home query) and `chat_messages.noteId` (full-scanned by three different queries); **DB v13→v14, `MIGRATION_13_14`**, index-only, no column or row touched. (9) **REL-15, the atomic-export-write half left open since v1.19.0** — `"wt"` truncates a target file and then writes, so a process death mid-write left a permanently truncated file at the real name, on an app whose exported Markdown is the only surviving copy once the in-app note is gone too. SAF's `renameDocument` can't overwrite an existing name, so true temp-then-rename-over-target doesn't work; instead the full new content goes to `<name>.tmp` first, the existing short-write check runs against *that* file, the real target is deleted only once the temp write is confirmed complete, and the temp is renamed into the now-free name. New `recoverStaleTempFile()` runs before anything else touches a given name: a stray `.tmp` with no real file present means a previous export crashed in exactly that window and gets promoted; a stray `.tmp` *alongside* an intact real file means the crash was earlier (or unrelated) and the temp is discarded. **Verified live for real, including the recovery branch that can actually be exercised without killing the process**: a normal export and a re-export both produced correct files with real frontmatter and a real transcript companion; a stray `.tmp` manually planted alongside an existing exported note (with a marker string absent from the real content) was correctly discarded — not promoted — by the next real export, which also correctly applied a genuine content edit made in the same pass. The crash-*during*-write branch itself (temp present, real file *absent*) still can't be triggered without killing the process mid-write and remains a named gap, same honesty standard REL-13's own file-lifecycle fix was held to. **All nine fixes together: 333 tests green (+1 over the 332 baseline — REL-18's migration test; the rest are hardware/threading/SAF-bound with no JVM-reachable seam, matching this codebase's own long-established boundary for exactly this class of fix).** Also as part of this same pass: **11 commits** brought a full session's backlog of previously-uncommitted work into git for the first time — see the two batch commit messages (AI-08/09/10/11 + CAP-23/24 + UX-22/23, and the sherpa-onnx migration) for what each covers; nothing from this session had been committed before this pass. Prior: **2026-08-10 (v1.19.0)** — **UX-18 + CAP-17 + CAP-16: Home searched by re-parsing the whole library on the UI thread, and the fallback recognizer had never produced a single word.** Three findings on the two surfaces the user actually touches. (1) **UX-18 — every keystroke in Home's search box re-derived every note, on the main thread.** `HomeViewModel.notes` is a `combine(...)` collected in `viewModelScope`, whose dispatcher is `Main.immediate`, and the filter called `NoteSearch.matches(note, query)` per note per keystroke: two JSON decodes (the body's segments and, on any miss, the far larger transcript) plus **seven `SimpleDateFormat` builds** for the searchable date spellings — at a couple of hundred notes, thousands of allocations and two JSON parses *per note per character typed*, all of it blocking frames. The list rows paid again, re-parsing `segmentsJson` for `preview` and formatting a date on every composition. Now a `HomeNoteIndex` derives each note's searchable text and display strings **once per note version**, validated by **reference identity** against the `NoteEntity` it was built from — Room hands out a fresh instance whenever a row changes, so an unchanged instance proves the derived text is current and a changed one always misses, which makes staleness impossible to get wrong (there is no fingerprint to keep in sync). Everything is lazy and independent: an empty query (Home's resting state) derives nothing, a note matching on its title never decodes its transcript, a filtered-out note never builds display strings. The filter itself moved to `Dispatchers.Default` via `flowOn`. (2) **CAP-17 — the LEGACY recognizer lane was dead code that reported itself as a broken microphone.** `SpeechRecognizer` is main-thread-only (`SpeechRecognizerImpl.checkIsCalledFromMainThread()` throws from the factory, `setRecognitionListener`, `startListening` and `cancel`), but `callbackFlow` runs its builder block in the **collector's** context — and the collector is `CaptureSessionManager.scope`, i.e. `Dispatchers.Default`. So the very first call threw, REL-11's error boundary caught it, and the user was told the mic was unavailable when the mic was fine. Every platform call now goes through an `onMain` helper, so the lane no longer depends on where the flow is collected from. (3) **CAP-16 — that same lane dropped words and span on failure.** The `callbackFlow`'s default 64-element buffer meant `trySend` could silently drop a *finalized utterance* (unbounded now — losing words the user said is the one failure this app must not have), and `onError` restarted on only three codes with **no delay**, so a persistent `ERROR_RECOGNIZER_BUSY` span as fast as the platform could reject it while every other code left the lane silently dead forever. Now: silence-shaped errors restart immediately, unrecoverable ones stop, everything else backs off 250ms→8s (doubling in a loop, not `shl` — Kotlin's `shl` uses only the low six bits of the shift count and would wrap back to a near-zero delay). Also **REL-15 (partial)**: a `"wt"` write that ends short without throwing (a full disk) no longer records a URI pointing at a truncated note; the atomic temp+rename half is **not** done and stays filed, because SAF's `renameDocument` cannot overwrite an existing name, so the atomic form needs a delete-then-rename that trades a millisecond truncation window for one with no file at all — and it cannot be tested without the `androidTest` harness (BLD-01). **213 tests** (was 190). Prior: **v1.18.0 — REL-14: a slow export could resurrect a note the user had just deleted.** Found by auditing the export/delete cascade — the app's *only* backup story (`allowBackup=false`, local-only; the exported Markdown is the copy that survives a wipe) and the last large component with **no tests at all**. Same shape as REL-13: the pure halves were covered, and the half that deletes and overwrites things was not. Four defects. (1) **`exportIfConfigured` wrote the whole row back after the export.** It read a `NoteEntity`, did slow SAF I/O, then called `noteDao.update(note.copy(obsidianFileUri = …))` — a full-row `@Update` built from a snapshot taken *before* the write — so anything the user did in that window was silently reverted when the export landed. The worst shape reads as corruption: **soft-delete a note while its export is in flight and `deletedAtEpochMs` goes back to null — the note reappears.** A hand-edit (`updateNoteContent`) or a recipe output landing in the same window was lost the same way. Now a two-column `setExportUris(id, noteUri, transcriptUri)` writes only what the export actually learned and cannot revert what it does not name; `migrateExports()` got the same treatment, where the window is a full SAF write per note across the entire library. (2) **The repair pass exported the whole backlog once per unexported note.** `exportIfConfigured` opportunistically calls `retryMissingExports()` after every success, guarded by `repairingExports` — but `exportMissing()` (Settings → **Export now**) never held that guard, so the first note's success exported all the others and the outer loop then walked its own stale list and exported each of them again: **measured at 9 exports for 5 notes**, i.e. ~2N writes and N full SAF directory scans behind a button the user is watching. (3) **`restore()` cleared `obsidianFileUri` but not `transcriptFileUri`**, so a restored note kept a live pointer to the companion `.transcript.md` the delete had already removed — benign while the re-export succeeds, and a write over an unrelated file if the provider recycled that document id. Both are cleared now, which is what the method's docstring already claimed. (4) **The unexported count could not see a missing transcript.** `obsidianFileUri IS NULL` was the whole test, so a note whose summary exported but whose companion transcript did not was neither counted by OBS-04 nor repaired by it — it read as backed up while the verbatim record, the half that cannot be regenerated, was missing. Two smaller ones went with them: `saveMergedNote`'s `getById(id)!!` (a bare `!!` in the merge path REL-10 spent a release protecting), and `deleteForever`, which now retries any export file the soft delete failed to remove — the row was the last thing pointing at it, so a transient SAF failure stranded an orphan permanently. **No schema change — DB stays v9** (all of these are `@Query`/repository changes; the Room identity hash is untouched). **190 tests green (22 new).** `NotesRepository` lost its `Context` and now depends on a new **`ExportSink`** interface (`data/export/ExportSink.kt` — deliberately *not* `ExportTarget`, which was INT-02's removed two-destination enum and would read as that concept returning; implemented by `NoteExporter`, which also absorbed the SAF `deleteDocument` — the export package owns those files' whole lifecycle), so the entire cascade runs on plain JVM fakes with no Room, no SAF and no device. **Each fix was confirmed by reverting it and watching exactly its own test fail** — 2 of 22 for (1), 1 for (2) reporting `expected:<5> but was:<9>`, 1 for (3), 1 for `deleteForever` — then restored. **Device-verified on the Pixel 9 Pro 2026-08-10**, in-place release-key update from v1.17.0 with every note intact and no migration error: a throwaway capture produced **both** files in the real export folder → **Delete** removed *both* (24 → 22 files), which is itself the proof the new two-column write-back persisted both URIs, since the cascade has nothing to delete otherwise → **Restore** re-exported both fresh (22 → 24) → **Delete now** left the folder **byte-identical to its starting listing**. Empty crash buffer, zero `TrailMix*` warnings. **Named gaps**: defect (1)'s resurrect race is a sub-second window, reproduced in the unit tests but not by hand on-device; defect (3)'s discriminating case (a restore whose re-export *fails*, leaving the stale pointer) likewise; and defect (4)'s widened SQL predicate is exercised on-device only in its negative direction — this device's DB legitimately has nothing missing a transcript, and the 11 July `.md` files sitting in the export folder are **not in the database at all** (they are the notes destroyed by the 2026-07-31 REL-07 uninstall, surviving only as exports), which is both why the count is correctly 0 and a standing reminder that there is still no import path (see INT-04). Prior: **v1.17.0 — REL-13: the crash journal could delete the transcript it failed to read, and eat the record after a truncated one.** Found by auditing the one component whose entire job is not losing a conference transcript. `CaptureJournal`'s *replay* was pure and well tested since REL-09; the **file** side around it — the half that actually deletes things — had no tests at all, and held two defects. (1) **`pending()` deleted any journal it could not read.** The branch was `if (session == null || !session.hasContent)`, where `session == null` means the *replay threw*, not that the journal was empty — so "I could not read this" and "this holds nothing" took the same destructive path, directly contradicting the comment three lines above it ("Deleting a recoverable transcript is the user's call and nobody else's"). The failures that land there correlate with **size** — an I/O error, or `runCatching` catching an `OutOfMemoryError` while folding a very long transcript — so the rule was at its most destructive on the longest session on the device, the one whose loss actually costs something. (2) **`adopt()` appended straight onto whatever the crash left behind.** A journal is reopened precisely *because* it was cut short, so a tail with no newline on it is the expected case there, not an exotic one; the next record was then glued onto the fragment and the combined line parsed as neither — so choosing **Continue capture** silently destroyed the first thing said after the recovery. The same shape exists on the live path: a `write` that throws part way (a full disk, i.e. exactly when the journal is load-bearing) left the stream mid-line and took the *next* record down with it. **Now**: an unreadable journal is logged and **kept** — invisible for that launch, costing only its bytes, versus a delete that cannot be undone; and both places a stream can sit mid-record close it first (`appendRecord` terminates a failed write, `ensureRecordBoundary` closes a recovered file before appending). A header that fails to write no longer abandons the journal either — replay already falls back to the start time encoded in the filename, so dropping it cost every utterance that followed for no gain. **No schema change — DB stays v9. 168 tests green (16 new).** The store's directory became a constructor parameter so the file logic runs on a temp dir with no device (Hilt still binds the `Context` constructor — verified in the generated `CaptureJournalStore_Factory`); `testOptions.unitTests.isReturnDefaultValues = true` was added because otherwise a class became untestable the moment it logged a warning. **Both defects were confirmed by reverting each fix and watching exactly its own test fail** (2 of 16), then restored. **Device-verified end to end on the Pixel 9 Pro 2026-08-10** across a *double* crash: capture → typed fragment → `am force-stop` → prompt reads `3:09 PM · 1:02 · 6 lines · typed notes` → **Continue capture** resumes at 1:07 on the continued timeline with fragment and transcript restored → second fragment → `am force-stop` again → **the same journal** (still stamped 3:09 PM, so `adopt()` reused the file) re-recovers at `1:52 · 10 lines`, i.e. the four records written *after* the adopt survived → **Save as note** produces a note holding both typed fragments and transcript lines from 0:17 to 1:23, spanning both crashes, created-at 3:09 PM (when the capture began, not when it was rescued) → relaunch shows no prompt, so the journal was deleted. Empty crash buffer throughout. **Named gap**: the truncated-tail repair itself is pinned by unit test only — reproducing it on-device would mean writing into app-private storage, which needs a debug build, and installing one over the release install would demand an uninstall (permanent note loss on an `allowBackup=false` app). Prior: **v1.16.0 — REL-12: the mic pump could be stranded, and the recorder freed out from under it.** Found by finishing the `AudioPipeline` audit REL-11 started. Three linked defects in shutdown, all in the *teardown* half that REL-11 did not touch. (1) **`AudioPipeline` never retained the read end of its own pipe** — `readSide` was a local, returned from `start()` and forgotten — so the pipeline could not guarantee its own shutdown. The mic pump blocks in `out.write()` once the pipe's ~64 KiB (about **two seconds** of 16 kHz mono) fills, and only the reader draining or the read end closing can unblock it. On every *abandon* path (pause, discard) the recognizer has already stopped draining, so the pump was relying on ML Kit closing an fd we had given away — a thread, two fds and the pipe buffer leaked per cancelled capture if it did not. (2) **`stop()` released the `AudioRecord` after a bounded `join(1_000)`** and released it *unconditionally* — so the one situation that makes the join time out (a wedged pump) was exactly the situation in which the native recorder was freed while that thread could still be inside `record.read()`. The playback lane twenty lines below already had this right: its pump owns its own `release()` in a `finally`. Same shape of asymmetry as REL-11's, in the same file. (3) **`stopCapture()` cancelled the listen job but never called `engine.endInput()`**, so the mic was released only when the cancelled recognizer flow finished unwinding — after ML Kit's `stopRecognition()`/`close()`, an IPC round trip into AICore. Until then the `AudioRecord` stayed open and the privacy indicator stayed lit *after the user had already stopped*. **Now**: the pipeline retains `readSide`; the mic pump owns the recorder's lifetime exactly like the playback pump; and `stop()` (graceful EOF — leaves the read end open so the recognizer flushes its tail) is split from **`release()`** (abandon — closes the read end *first*, turning a blocked `out.write()` into an immediate EPIPE), with `CaptureEngine.teardownPipeline()` calling the latter. `stopCapture()` now calls the idempotent `endInput()` up front. **No schema change — DB stays v9. 152 tests green.** `AudioPipeline` has **no unit tests and gets none here** — it is bound to real `AudioRecord` hardware, and faking that would mean an interface extraction larger than the fix; this rests on inspection plus device evidence. **Device-verified on the Pixel 9 Pro 2026-08-10** with a direct observable rather than an inference: `adb shell ps -T` for the `trailmix-mic-pump` thread alongside `dumpsys audio`'s `RecordActivityMonitor`. During capture — 1 pump thread, `riid 81559; active? true … pack:com.trailmix.app`. **Pause → within 1 s: 0 pump threads and `RecordActivityMonitor` completely empty.** Resume → **exactly one** pump thread and one fresh recorder (`riid 81567`), i.e. no accumulation across a pause/resume. End & Merge → within 2 s: 0 pump threads, mic released, FGS re-typed to `types=0x00000001` (DATA_SYNC) and held there for the merge (REL-10 still good). After the full cycle: **0 `trailmix-` threads left in the process**, pid unchanged throughout (no crash), empty crash buffer, and zero warnings from `TrailMixAudio`/`TrailMixEngine`/`TrailMixSession`/`TrailMixAsr`. The tail-flush regression risk was checked directly, not assumed: the resulting note carries content from **both sides of the pause** and its final line lands at **2:01**, the last utterance before the tap — so the graceful drain still delivers the recognizer's tail. **Named gap**: the wedged-pump branch itself is still not induced on-device (it needs the recognizer to stall while the mic runs), so (1) and (2) are fixed by construction and inspection, not by live repro. Prior: **v1.15.0 — REL-11: a busy microphone crashed the app.** Found by auditing the capture lifecycle for reliability, not from a report. `AudioPipeline.start()` checked the *device-audio* lane's `AudioRecord.state` but never the **mic** lane's — and `AudioRecord` does not throw when it fails to acquire the mic, it constructs in `STATE_UNINITIALIZED` and throws later from `startRecording()`. That `IllegalStateException` escaped `CaptureEngine.begin()` into `listenJob = scope.launch { … }`, which had no `try`/`catch`, on a scope with **no `CoroutineExceptionHandler` anywhere in the codebase** — so it reached the default handler and **killed the process**. The trigger is ordinary: anything else holding the mic (a call, another recorder, the assistant), and "start a capture during a call" is a scenario CAP-12 explicitly supports. A second defect sat behind it: `running = true` was set *before* `startRecording()`, so the throw left it true forever and every later `start()` hit `check(!running)` — the pipeline was bricked for the rest of the process, with the `AudioRecord` and both pipe fds leaked on each retry. **Now**: the mic lane is state-checked exactly like the playback lane; failure releases the recorder, closes both pipe ends (`abandonPipe`, closing the wrapping stream rather than the fd twice) and resets `running`; and it throws a typed `AudioUnavailableException` that `CaptureEngine` treats as a *start* failure, dropping through the same fail-soft ladder every other capability uses. `CaptureSessionManager`'s listen body moved to `runListenSession()` inside one error boundary that rethrows `CancellationException` (teardown depends on that handshake) and otherwise reports it; the scope gained a `CoroutineExceptionHandler` backstop so an *unanticipated* throw in any of its ~15 `launch` sites degrades to a logged error and a stopped capture rather than a dead process. New `CaptureUiState.captureError` carries the situational reason, because the existing `speechAvailable = false` copy reads "isn't available on this device" — actively wrong for a mic that is merely busy. **No schema change — DB stays v9. 152 tests green.** Smoke-tested on the Pixel 9 Pro (capture → typed fragment → End & Merge → note, empty crash buffer, no engine warnings); **the mic-contention branch itself is NOT device-verified** — inducing it means holding the mic with another app, which was judged not worth doing to the user's real device. Prior: **v1.14.0 — REL-10: the merge no longer runs unprotected, and a failed merge no longer bricks capture.** Found by reading the capture lifecycle, not from a report. Three defects, all of which only bite at the scale this app is aimed at. (1) **`endAndMerge` tore down the foreground service one line *before* the merge ran.** `stopCapture()` called `CaptureService.stop()` → `stopForeground(REMOVE)` + `stopSelf()`, and only then did the map-reduce merge start — which `LongSessionLoadTest` sizes at ~a dozen sequential AICore calls, i.e. **minutes**, for a 90-minute keynote. So the process spent the entire merge with **no foreground component**, ordinary low-memory-killer fodder the moment the user left the app; REL-09's journal made that survivable rather than fatal, but the merge itself was lost and the user was handed a "recover?" prompt for a note they thought they had saved. This also falsified a claim in [[Future Improvements]] that leaving the app mid-merge was "safe by design — it runs behind the capture foreground service"; it did not. (2) **The notification vanished at the same instant**, so TrailMix disappeared from the shade while doing minutes of work — and `CaptureService` already *had* a "Merging on-device…" branch that was simply unreachable, because the service was destroyed before it could render it. New pure `data/speech/MergeStatus.kt` drives a **progress** line and bar (`Summarizing 3 of 6…` → `Writing the note…`) in both the notification and the Capture screen, fed by a new `onProgress` callback through `OnDeviceAiProcessor.merge`. That is not decoration: a frozen label for several minutes reads as a hang, and the user's remedy for a hang is to force-stop the app — killing the very merge this change exists to protect. **No schema change — DB stays v9. 152 tests green (7 new). ## Non-negotiable Principles
- **Documentation is mandatory after ANY change** — (1) update the owning vault note(s) per the Documentation Handoff Map, (2) update repo `README.md` if user-facing behavior/config changed, (3) commit locally and push to `github` (see Project Facts for the remote), (4) move shipped items to Complete in [[Future Improvements]] **the moment they're verified complete — same session, even mid-batch before the version ships** (tag the Complete entry `vX.Y.Z-dev` + commit hashes until the release lands, then fold it into the release row). The To-Do table must never hold a row whose Status says done: a completed row sitting in To-Do is stale data that misleads the next session's backlog parse.
- **Verify `README.md` is still accurate every session**, not only when something changes — paths, build commands, version/platform status. A stale README (e.g. a build command that no longer matches the repo layout) is a real regression even if no code changed. (Added 2026-07-15 after the `Android/` restructure — a great way for exactly this kind of drift to happen unnoticed.)
- **Local-only is the product — zero network permission, with no disclosed exception currently open (v1.20.0-dev, restored 2026-09-13).** Any cloud API, telemetry, crash reporting, or analytics stays permanently declined, not merely deferred — that has not changed. History, kept because it explains code shape that's still in the tree: AI-01 speaker diarization briefly needed `INTERNET`, via Picovoice Falcon, solely to validate the user's own Picovoice AccessKey — diarization itself ran fully on-device, and no audio/transcript/note content was ever transmitted; a second Picovoice product, Eagle (persistent/live speaker recognition), rode the same disclosed exception rather than opening a new one. **Both are gone as of the same-session sherpa-onnx migration (all three phases, 2026-09-13)**: diarization now runs via the vendored `sherpa-onnx` AAR and Eagle's scaffolding was deleted outright (zero callers, no enrollment UI ever shipped) — see the Falcon and Eagle rows below for the full migration writeup, the two real device bugs Phase 1 found, and the empirical `aapt2 dump permissions` confirmation that neither `INTERNET` nor `ACCESS_NETWORK_STATE` remain. The real rule was never "zero network bytes," it is **"no user data leaves the device"** — a pure license/usage validation ping with no user content in the payload was a judgement call raised and approved at the time (not assumed), not an automatic disqualifier, and the same reasoning applies if a future feature ever raises the same question again; this is not a precedent against it, just a record that it happened once and was fully rolled back once a better option existed. A future sherpa-onnx-based Phase 4 (AI-12 enrollment/recognition, not yet built) needs no key or account of any kind, so it is not expected to reopen this question. Since v1.7.0 (INT-02) there is still **no dedicated cloud-sync feature** — the dedicated Google Drive sync was removed by user decision (do not re-suggest it; see [[Future Improvements]]'s declined list). Residual nuance unchanged: the user-picked Export location is any SAF folder, and if that folder happens to be synced by another app, that app may upload the files. Any future export surface must stay SAF/DocumentsProvider-only, never an in-process network SDK.
- **Zero-retention audio is architectural, not policy** — no code path may ever write captured audio to disk. The recognizer consumes the mic stream in memory; keep it that way.
- **All AI stays on-device and fail-soft** — every AI consumer must produce a deterministic fallback result when Gemini Nano is absent, downloading, or erroring. The app must be fully usable with no model at all.
- **Confirm before anything disruptive or irreversible** — deleting user notes/data, changing the DB schema destructively, loosening any permission or the security posture, force-pushing (the one-time, user-authorized `main` history replacement documented in [[Future Improvements]]'s REL-05 Complete entry is done — it is not a standing exception; never force-push again).
- **Schema changes are additive** — Room migrations only add. The app holds real user notes, so `fallbackToDestructiveMigration()` is **gone**: every version bump that changes the schema ships an explicit `Migration` (see `MIGRATION_2_3` through `MIGRATION_7_8` in `di/AppModule.kt`; DB is at **v9** — v1.11.0's `MIGRATION_8_9` added `notes.transcriptFileUri` for OBS-02's companion transcript file) and increments the DB version. Retired columns (`notes.driveFileUri`) go dormant, never dropped. Never destructive-fallback again.
- **New permissions require explicit user sign-off** and must be runtime-requested, opt-in, and justified in [[Security and Privacy]]. (v1.7.0 added no new permission.)
- Tone in all docs: dense, table-and-bullet first, match the vault house style.
