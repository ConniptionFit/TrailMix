Last updated: **2026-08-10 (v1.17.0)** — **REL-13: the crash journal could delete the transcript it failed to read, and eat the record after a truncated one.** Found by auditing the one component whose entire job is not losing a conference transcript. `CaptureJournal`'s *replay* was pure and well tested since REL-09; the **file** side around it — the half that actually deletes things — had no tests at all, and held two defects. (1) **`pending()` deleted any journal it could not read.** The branch was `if (session == null || !session.hasContent)`, where `session == null` means the *replay threw*, not that the journal was empty — so "I could not read this" and "this holds nothing" took the same destructive path, directly contradicting the comment three lines above it ("Deleting a recoverable transcript is the user's call and nobody else's"). The failures that land there correlate with **size** — an I/O error, or `runCatching` catching an `OutOfMemoryError` while folding a very long transcript — so the rule was at its most destructive on the longest session on the device, the one whose loss actually costs something. (2) **`adopt()` appended straight onto whatever the crash left behind.** A journal is reopened precisely *because* it was cut short, so a tail with no newline on it is the expected case there, not an exotic one; the next record was then glued onto the fragment and the combined line parsed as neither — so choosing **Continue capture** silently destroyed the first thing said after the recovery. The same shape exists on the live path: a `write` that throws part way (a full disk, i.e. exactly when the journal is load-bearing) left the stream mid-line and took the *next* record down with it. **Now**: an unreadable journal is logged and **kept** — invisible for that launch, costing only its bytes, versus a delete that cannot be undone; and both places a stream can sit mid-record close it first (`appendRecord` terminates a failed write, `ensureRecordBoundary` closes a recovered file before appending). A header that fails to write no longer abandons the journal either — replay already falls back to the start time encoded in the filename, so dropping it cost every utterance that followed for no gain. **No schema change — DB stays v9. 168 tests green (16 new).** The store's directory became a constructor parameter so the file logic runs on a temp dir with no device (Hilt still binds the `Context` constructor — verified in the generated `CaptureJournalStore_Factory`); `testOptions.unitTests.isReturnDefaultValues = true` was added because otherwise a class became untestable the moment it logged a warning. **Both defects were confirmed by reverting each fix and watching exactly its own test fail** (2 of 16), then restored. **Device-verified end to end on the Pixel 9 Pro 2026-08-10** across a *double* crash: capture → typed fragment → `am force-stop` → prompt reads `3:09 PM · 1:02 · 6 lines · typed notes` → **Continue capture** resumes at 1:07 on the continued timeline with fragment and transcript restored → second fragment → `am force-stop` again → **the same journal** (still stamped 3:09 PM, so `adopt()` reused the file) re-recovers at `1:52 · 10 lines`, i.e. the four records written *after* the adopt survived → **Save as note** produces a note holding both typed fragments and transcript lines from 0:17 to 1:23, spanning both crashes, created-at 3:09 PM (when the capture began, not when it was rescued) → relaunch shows no prompt, so the journal was deleted. Empty crash buffer throughout. **Named gap**: the truncated-tail repair itself is pinned by unit test only — reproducing it on-device would mean writing into app-private storage, which needs a debug build, and installing one over the release install would demand an uninstall (permanent note loss on an `allowBackup=false` app). Prior: **v1.16.0 — REL-12: the mic pump could be stranded, and the recorder freed out from under it.** Found by finishing the `AudioPipeline` audit REL-11 started. Three linked defects in shutdown, all in the *teardown* half that REL-11 did not touch. (1) **`AudioPipeline` never retained the read end of its own pipe** — `readSide` was a local, returned from `start()` and forgotten — so the pipeline could not guarantee its own shutdown. The mic pump blocks in `out.write()` once the pipe's ~64 KiB (about **two seconds** of 16 kHz mono) fills, and only the reader draining or the read end closing can unblock it. On every *abandon* path (pause, discard) the recognizer has already stopped draining, so the pump was relying on ML Kit closing an fd we had given away — a thread, two fds and the pipe buffer leaked per cancelled capture if it did not. (2) **`stop()` released the `AudioRecord` after a bounded `join(1_000)`** and released it *unconditionally* — so the one situation that makes the join time out (a wedged pump) was exactly the situation in which the native recorder was freed while that thread could still be inside `record.read()`. The playback lane twenty lines below already had this right: its pump owns its own `release()` in a `finally`. Same shape of asymmetry as REL-11's, in the same file. (3) **`stopCapture()` cancelled the listen job but never called `engine.endInput()`**, so the mic was released only when the cancelled recognizer flow finished unwinding — after ML Kit's `stopRecognition()`/`close()`, an IPC round trip into AICore. Until then the `AudioRecord` stayed open and the privacy indicator stayed lit *after the user had already stopped*. **Now**: the pipeline retains `readSide`; the mic pump owns the recorder's lifetime exactly like the playback pump; and `stop()` (graceful EOF — leaves the read end open so the recognizer flushes its tail) is split from **`release()`** (abandon — closes the read end *first*, turning a blocked `out.write()` into an immediate EPIPE), with `CaptureEngine.teardownPipeline()` calling the latter. `stopCapture()` now calls the idempotent `endInput()` up front. **No schema change — DB stays v9. 152 tests green.** `AudioPipeline` has **no unit tests and gets none here** — it is bound to real `AudioRecord` hardware, and faking that would mean an interface extraction larger than the fix; this rests on inspection plus device evidence. **Device-verified on the Pixel 9 Pro 2026-08-10** with a direct observable rather than an inference: `adb shell ps -T` for the `trailmix-mic-pump` thread alongside `dumpsys audio`'s `RecordActivityMonitor`. During capture — 1 pump thread, `riid 81559; active? true … pack:com.trailmix.app`. **Pause → within 1 s: 0 pump threads and `RecordActivityMonitor` completely empty.** Resume → **exactly one** pump thread and one fresh recorder (`riid 81567`), i.e. no accumulation across a pause/resume. End & Merge → within 2 s: 0 pump threads, mic released, FGS re-typed to `types=0x00000001` (DATA_SYNC) and held there for the merge (REL-10 still good). After the full cycle: **0 `trailmix-` threads left in the process**, pid unchanged throughout (no crash), empty crash buffer, and zero warnings from `TrailMixAudio`/`TrailMixEngine`/`TrailMixSession`/`TrailMixAsr`. The tail-flush regression risk was checked directly, not assumed: the resulting note carries content from **both sides of the pause** and its final line lands at **2:01**, the last utterance before the tap — so the graceful drain still delivers the recognizer's tail. **Named gap**: the wedged-pump branch itself is still not induced on-device (it needs the recognizer to stall while the mic runs), so (1) and (2) are fixed by construction and inspection, not by live repro. Prior: **v1.15.0 — REL-11: a busy microphone crashed the app.** Found by auditing the capture lifecycle for reliability, not from a report. `AudioPipeline.start()` checked the *device-audio* lane's `AudioRecord.state` but never the **mic** lane's — and `AudioRecord` does not throw when it fails to acquire the mic, it constructs in `STATE_UNINITIALIZED` and throws later from `startRecording()`. That `IllegalStateException` escaped `CaptureEngine.begin()` into `listenJob = scope.launch { … }`, which had no `try`/`catch`, on a scope with **no `CoroutineExceptionHandler` anywhere in the codebase** — so it reached the default handler and **killed the process**. The trigger is ordinary: anything else holding the mic (a call, another recorder, the assistant), and "start a capture during a call" is a scenario CAP-12 explicitly supports. A second defect sat behind it: `running = true` was set *before* `startRecording()`, so the throw left it true forever and every later `start()` hit `check(!running)` — the pipeline was bricked for the rest of the process, with the `AudioRecord` and both pipe fds leaked on each retry. **Now**: the mic lane is state-checked exactly like the playback lane; failure releases the recorder, closes both pipe ends (`abandonPipe`, closing the wrapping stream rather than the fd twice) and resets `running`; and it throws a typed `AudioUnavailableException` that `CaptureEngine` treats as a *start* failure, dropping through the same fail-soft ladder every other capability uses. `CaptureSessionManager`'s listen body moved to `runListenSession()` inside one error boundary that rethrows `CancellationException` (teardown depends on that handshake) and otherwise reports it; the scope gained a `CoroutineExceptionHandler` backstop so an *unanticipated* throw in any of its ~15 `launch` sites degrades to a logged error and a stopped capture rather than a dead process. New `CaptureUiState.captureError` carries the situational reason, because the existing `speechAvailable = false` copy reads "isn't available on this device" — actively wrong for a mic that is merely busy. **No schema change — DB stays v9. 152 tests green.** Smoke-tested on the Pixel 9 Pro (capture → typed fragment → End & Merge → note, empty crash buffer, no engine warnings); **the mic-contention branch itself is NOT device-verified** — inducing it means holding the mic with another app, which was judged not worth doing to the user's real device. Prior: **v1.14.0 — REL-10: the merge no longer runs unprotected, and a failed merge no longer bricks capture.** Found by reading the capture lifecycle, not from a report. Three defects, all of which only bite at the scale this app is aimed at. (1) **`endAndMerge` tore down the foreground service one line *before* the merge ran.** `stopCapture()` called `CaptureService.stop()` → `stopForeground(REMOVE)` + `stopSelf()`, and only then did the map-reduce merge start — which `LongSessionLoadTest` sizes at ~a dozen sequential AICore calls, i.e. **minutes**, for a 90-minute keynote. So the process spent the entire merge with **no foreground component**, ordinary low-memory-killer fodder the moment the user left the app; REL-09's journal made that survivable rather than fatal, but the merge itself was lost and the user was handed a "recover?" prompt for a note they thought they had saved. This also falsified a claim in [[Future Improvements]] that leaving the app mid-merge was "safe by design — it runs behind the capture foreground service"; it did not. (2) **The notification vanished at the same instant**, so TrailMix disappeared from the shade while doing minutes of work — and `CaptureService` already *had* a "Merging on-device…" branch that was simply unreachable, because the service was destroyed before it could render it. (3) **A merge that threw left `merging = true` forever.** `endAndMerge` had no error handling at all (`completeRecovered` did), and every entry point — `startCapture`, `resume`, `endAndMerge`, `completeRecovered` — early-returns on `merging`, so **one failed merge made the app unable to record again until it was force-stopped**, with the Capture screen stuck on a spinner because `onDone` was never called either. **Now**: `stopCapture(handOffToMerge = true)` hands the service to a merge phase instead of killing it — re-typed from `microphone` to **`dataSync`** (new `FOREGROUND_SERVICE_DATA_SYNC` permission; normal-protection, no prompt, **not** a network capability) so the mic privacy indicator stops implying TrailMix is still listening, while the process stays foreground; the merge body moved to `runMerge()` with unconditional teardown around it, so `merging` always clears and `onDone` always fires; and `completeRecovered` — whose own docstring already said it "can take minutes" — gets the same protection, having previously run with no foreground component at all. New pure `data/speech/MergeStatus.kt` drives a **progress** line and bar (`Summarizing 3 of 6…` → `Writing the note…`) in both the notification and the Capture screen, fed by a new `onProgress` callback through `OnDeviceAiProcessor.merge`. That is not decoration: a frozen label for several minutes reads as a hang, and the user's remedy for a hang is to force-stop the app — killing the very merge this change exists to protect. **No schema change — DB stays v9. 152 tests green (7 new). Device-verified on the Pixel 9 Pro 2026-08-10**, and the headline claim was *measured*, not inferred: sampling `dumpsys activity services` across an End & Merge gave `types=0x00000080` (MICROPHONE, alive) → tap → `types=0x00000001` (DATA_SYNC, still `isForeground=true`) → service gone 16 s later, i.e. the whole merge held behind a foreground service where it previously ran as a killable background process. Notification during that window: note name as title, `"Merging on-device…"`, indeterminate progress, **no actions** (vs `actions=2` recording), visible in the shade with the app backgrounded and above the `Silent` divider. Crash buffer empty across ~6 merges; a real `AiCoreInferenceHelper statusCode = 30` occurred mid-pass and failed soft with a clean teardown. **The pass found one more defect and fixed it (`6a4d451`)**: Android's collapsed template draws the progress bar *in place of* the content-text line, so the shade showed the note name and a bar and nothing else — the `Summarizing N of M…` count was invisible unless expanded. The label now also goes to `setSubText` (collapsed header). **Named gaps**: the determinate `N of M` path is unexercised (every test session was one chunk — needs 10+ min of speech), the collapsed row's subtext is confirmed from notification extras but not photographed, the mic privacy indicator clearing is inferred from the type change rather than observed, and defect 3's throw path never fired (the AICore failure is caught inside `OnDeviceAiProcessor`, so it never reaches `runMerge`'s `runCatching`). Prior: **v1.13.0** — **REL-09: a capture no longer dies with the process.** Until now a session existed only in `CaptureSessionManager`'s in-memory buffers until End & Merge wrote a note, so a crash, a low-memory kill while the user was in another app, force-stop, or a flat battery took the **entire transcript** with it and left nothing behind to show it had happened. That is the worst data-loss shape this app has and the likeliest moment for it is the one that matters most (a long backgrounded session competing for memory). Now every finalized utterance is appended to an **append-only JSONL write-ahead journal** in app-private `filesDir`, flushed and `fsync`ed as it is recognized; session metadata follows as last-wins delta records on a 10 s timer. A leftover journal is replayed on next launch and offered back on Home: **Continue capture / Save as note / Later / Discard** (confirm-gated). Append-only is the design, not an implementation detail: a crash can only truncate the *last* record, and the cost is O(n) bytes rather than the ~95 MB an O(n²) per-utterance re-serialise would have written over a 90-minute keynote. ## Identity & Purpose

You are an LLM IDE agent responsible for reviewing, maintaining, and extending **TrailMix** — a **local-only, security-conscious Android app** (Kotlin + Jetpack Compose) that captures live mic transcripts during calls/meetings, lets the user type rough fragments alongside, and merges both **fully on-device** into a provenance-tagged note with chat/recipe follow-ups. A good session: check reality against docs before trusting either, make a scoped change through exactly one capability module, verify it compiles (and on a device when one is attached), and leave **both the Obsidian vault and the repo** accurately reflecting what changed.

## Non-negotiable Principles
- **Documentation is mandatory after ANY change** — (1) update the owning vault note(s) per the Documentation Handoff Map, (2) update repo `README.md` if user-facing behavior/config changed, (3) commit locally and push to `github` (see Project Facts for the remote), (4) move shipped items to Complete in [[Future Improvements]] **the moment they're verified complete — same session, even mid-batch before the version ships** (tag the Complete entry `vX.Y.Z-dev` + commit hashes until the release lands, then fold it into the release row). The To-Do table must never hold a row whose Status says done: a completed row sitting in To-Do is stale data that misleads the next session's backlog parse.
- **Verify `README.md` is still accurate every session**, not only when something changes — paths, build commands, version/platform status. A stale README (e.g. a build command that no longer matches the repo layout) is a real regression even if no code changed. (Added 2026-07-15 after the `Android/` restructure — a great way for exactly this kind of drift to happen unnoticed.)
- **Local-only is the product.** Never add the `INTERNET` permission, any cloud API, telemetry, crash reporting, or analytics — these are permanently declined, not merely deferred. Any feature that "needs network" needs a redesign instead. Since v1.7.0 (INT-02) there is **no dedicated cloud-sync feature at all** — the dedicated Google Drive sync was removed by user decision (do not re-suggest it; see [[Future Improvements]]'s declined list). The honest residual nuance: the user-picked Export location is any SAF folder, and if that folder happens to be synced by another app, that app may upload the files — TrailMix itself only ever writes locally and never gains `INTERNET`. Any future export surface must stay SAF/DocumentsProvider-only, never an in-process network SDK.
- **Zero-retention audio is architectural, not policy** — no code path may ever write captured audio to disk. The recognizer consumes the mic stream in memory; keep it that way.
- **All AI stays on-device and fail-soft** — every AI consumer must produce a deterministic fallback result when Gemini Nano is absent, downloading, or erroring. The app must be fully usable with no model at all.
- **Confirm before anything disruptive or irreversible** — deleting user notes/data, changing the DB schema destructively, loosening any permission or the security posture, force-pushing (the one-time, user-authorized `main` history replacement documented in [[Future Improvements]]'s REL-05 Complete entry is done — it is not a standing exception; never force-push again).
- **Schema changes are additive** — Room migrations only add. The app holds real user notes, so `fallbackToDestructiveMigration()` is **gone**: every version bump that changes the schema ships an explicit `Migration` (see `MIGRATION_2_3` through `MIGRATION_7_8` in `di/AppModule.kt`; DB is at **v9** — v1.11.0's `MIGRATION_8_9` added `notes.transcriptFileUri` for OBS-02's companion transcript file) and increments the DB version. Retired columns (`notes.driveFileUri`) go dormant, never dropped. Never destructive-fallback again.
- **New permissions require explicit user sign-off** and must be runtime-requested, opt-in, and justified in [[Security and Privacy]]. (v1.7.0 added no new permission.)
- Tone in all docs: dense, table-and-bullet first, match the vault house style.

## Backlog

Work open rows in the **To-Do table** in [[Future Improvements]] (priority then table order) unless directed otherwise. Check the **Declined list** at the top of that file before proposing anything resembling it — it now also carries the v1.7.0 removed-by-user-decision items (Drive sync, Name Variants, Sales Pitch template): do not re-suggest re-adding them. Items whose Details say "user decision" get sign-off **before implementation**.

**Filing new work.** Any new work item — from a user request, a bug report, or an idea — must become a new row in the To-Do table using the exact schema `| ID | Priority | Category | Item | Details | Requested |`. Model the wording on a good existing row: terse but complete: what's broken/missing, what the fix would touch, any constraint that matters. It must get a fresh, permanent ID using one of the existing prefixes (`REL-`, `CAP-`, `AI-`, `UX-`, `SEC-`, `LIN-`, `OBS-`, `CAL-`, `INT-`) or a new prefix if it's genuinely a new category — **never** left as an untabled bullet, **never** reusing or renumbering an ID even after the row ships or is declined (old session notes and code comments reference IDs permanently). A **"Feature Ideas & Innovation Opportunities"** section (bulleted, not tabled) is the only acceptable place for a not-yet-triaged idea to sit outside the To-Do table — and even there, the moment someone decides to act on it, promote it to a proper To-Do row with an ID (mark the bullet `*Promoted:* see **ID** in To-Do` or delete it) rather than building it while still a bullet.

Ship a row → move it to Complete with version/date, **immediately upon verification, not at the eventual version release** — mid-batch completions go in as `vX.Y.Z-dev` + commit hashes and get folded into the release row when the version ships. Partially-done rows stay in To-Do with an honest **Status** clause; fully-done rows never do. If an audit turns up a row that's already implemented but was never formally shipped through this process, move it to Complete too, marked with an honest `found complete during <date> audit` note in place of a version — don't fabricate a version/date it doesn't have.
